# 手感优化方案：消除"单位卡淤积 + 附魔重复拖拽"

> 目标：**只解决"烦"**——降低操作摩擦与手牌淤积，不引入战棋/阵地等新玩法。
> 战棋方向（波次预告、地块、朝向、驻守巩固）另立文档，等本方案验证后再谈。
>
> 状态：方案待评审，未开始实现。

---

## 一、诊断：烦来自四个具体摩擦点

先给结论：**现在的烦不是"抽到太多单位卡"，而是"手牌利用率极低 + 附魔操作频次极高"。**

### 摩擦点 1：能量饥荒让手牌长期是废牌

| 项 | 数值 | 出处 |
|---|---|---|
| 初始能量 | 4 | `BALANCE.playerEnergy.initial`，`src/data/gameData.js` |
| 能量回复 | **0.1 / 秒 = 6 / 分钟** | `BALANCE.playerEnergy.regenerationPerSecond` |
| 单位卡费用 | 2 ~ 4（均值 3.38） | `CARD_DEFINITIONS` 的 `energyCost` |
| 附魔卡费用 | 2 ~ 3（均值 2.05） | 同上 |
| 手牌上限 | **10** | `HAND_SIZE`，`src/systems/CardSystem.js:12` |
| 活跃牌库 | **12** | `ACTIVE_DECK_SIZE`，`src/data/gameData.js:7` |
| 弃牌费 | **1** | `discardEnergyCost()`，`src/systems/CardSystem.js:3712` |

推论：开局手牌 10 张，活跃牌库只有 12 张（`CardSystem` 构造函数把 12 张洗入 `drawPile`，再抽满 10 张手牌，`drawPile` 只剩 2 张）。也就是说**玩家从第一秒起就看着 83% 的牌库**，而每分钟只有 6 点能量、平均每张牌要 2~3 点 → **一分钟只能打出 2~3 张，剩下 7~8 张手牌全程是死的**。这不是抽卡问题，是能量节流问题。

### 摩擦点 2：附魔卡占了牌池 41%，最容易被抽到

完整牌池分布（`src/data/gameData.js`）：

| kind | 张数 |
|---|---|
| enchant | **38** |
| ability | 23 |
| summon | 16 |
| spell | 6 |
| tactic | 6 |
| building | 4 |

附魔卡不仅是最大类，还**单价 2 点**（和便宜单位卡同价），于是"手牌里一堆附魔、能量不够用"成为常态。

### 摩擦点 3：每一次附魔升级 = 一次完整拖拽

现状流程（`src/systems/CardSystem.js`）：

1. 把附魔卡从手牌拖到某个友方单位身上（`updateDrag` 的 `target === 'friendly-unit'` 分支，约 729~763 行），靠射线拾取单个单位；
2. 松手施放一次 → 卡回手 → 想再升一级，**必须再拖一次**；
3. 长按连发只解决"同一个目标连点"：`ENCHANT_HOLD_START_MS = 350`、`ENCHANT_HOLD_TICK_MS = 1000`（`CardSystem.js:44-47`）→ 升到 5 级需要 **350ms + 4×1000ms ≈ 4.35 秒**持续按住不动；
4. 期间鼠标移出目标、目标死亡、或进入弃牌区，连发即中断；且**连发只作用于单个单位**。

结论：**操作次数 = 单位数 × 附魔类型 × 等级**。这是纯粹的手指税。

### 摩擦点 4：弃牌太贵，死牌出不去，进一步加剧"手牌全是废牌"的感觉

弃一张 1 点能量，而每分钟只有 6 点 → 玩家宁愿"忍着手牌满"也不愿弃牌，于是死牌长期占位。

## 二、修复候选（按收益/成本排序）

### R1：能量从"滴灌"改成"节奏化供给"（核心）

只调一个数就能让每分钟可打出的牌翻倍：

```js
// src/data/gameData.js, BALANCE.playerEnergy
initial: 4,
regenerationPerSecond: 0.18   // 0.1 → 0.18（分钟产出 6 → 10.8）
```

更推荐的做法是**基础回复 + 战斗事件奖励**，让能量供给带上节奏：

| 来源 | 建议值 | 理由 |
|---|---|---|
| 基础回复 | 0.16 / 秒 | 保留资源紧张感 |
| 击杀回能 | 0.4 / 击杀 | 鼓励主动交战，打得越猛打得越快 |
| 每波清空 | +4 | 波次之间给一个"喘息窗口"，节奏更清晰 |

风险与对冲：
- 风险：单位变多，敌方缩放（`enemyForceRules` / `endlessMode`）相对变弱。
- 对冲：先做 R1 的基础回复部分（0.1 → 0.16）跑一局观察同屏单位数，再决定是否加击杀回能。**不要一次全上。**

### R2：附魔卡费用 2 → 1

附魔是"加法"而不是"新单位"，单价应该低于单位卡。降到 1 后，同样的能量可以"一个单位 + 一次附魔"，而不是"只能二选一"。

风险与对冲：可能出现"只附魔不出兵"。用一个可观测指标守住——**每局附魔施放次数 / 单位召唤次数**，若大于 3 就回调到 2 或给附魔加短冷却。

### R3：附魔区域施加（把 N 次拖拽压成 1 次）

在现有 drag 流程里新增一个"区域模式"：

- 触发：拖拽附魔卡时按住 `Shift`（或长按 600ms）切到区域模式；
- 表现：复用 `showGroundPreview()`（`CardSystem.js:871`）的半径预览，把有效目标从"单个单位"改成"半径 R 内的所有友方单位"，命中单位高亮复用 `showEnchantPreview()` 的环形标记；
- 结算：**不要客户端把 N 个单位 id 发给 host**（`CommandValidator.validateCard` 目前只校验单个 `targetUnitId`，`src/network/host/CommandValidator.js:160`）。改为**发给 host 一个地面点 + 半径，由 host 权威地重算受影响的单位列表**，保证联机确定性；
- 费用：按受影响单位数 × 卡费结算（这样不会用一张卡白嫖全场），卡面上实时显示 `×N 单位 / 消耗 M 能量`。

默认 R 建议 5~6（约等于 `playerBase.recoveryRadius: 4.8` 的量级）。

### R4：同名附魔施加到同目标 = 等级 +1，不占新槽

现在同名附魔已有 id 时会被 `isEnchantmentSlotFull()`（`src/systems/enchantmentSlots.js`）跳过，等价于"白拖一次"。改成**等级 +1**，玩家手感上就是"两个火附魔 = 火II"，天然减少重复拖拽；5 个槽位真正留给 5 种不同附魔。

### R5：单位卡两两合成（可选）

手牌中两张同名单位卡自动合成一张 +1 级卡，拖一次出高级单位。复用已有的 `upgradeCardFamily()`（`CardSystem.js:1733`）。
放在 R1~R4 之后做，因为它动的是手牌 UI 与合成动画，收益不如前四条直接。

### 明确不做（本轮）

- ❌ 降低单位卡伤害/血量来"减少单位数量"——这会破坏现有平衡。
- ❌ 把附魔改成装备栏/棋盘等新系统——超出"只解决烦"的范围。
- ❌ 战棋相关的一切（波次预告、地块、朝向、驻守巩固）——见后续文档。

## 三、推荐落地顺序

### 阶段一（低风险，先验证手感）
1. **R1 基础部分**：`regenerationPerSecond: 0.1 → 0.16`
2. **R2**：附魔卡 `energyCost: 2 → 1`（38 张批量改）
3. **R4**：同名附魔同目标等级 +1

验收：一局打完，主观感受"手牌不再是废牌堆"，且**单位召唤次数没有暴涨**（对比改动前后同屏最大单位数）。

### 阶段二（中等风险，解决附魔疲劳）
4. **R3**：附魔区域施加（含 host 权威重算 + 联机命令协议扩展）

验收：一次拖拽给 3~5 个单位铺附魔，操作次数从 N 降到 1；联机双方附魔结果完全一致。

### 阶段三（可选）
5. **R5** 单位卡合成；必要时再加 R1 的击杀回能。

## 四、联机兼容性（硬约束）

`docs/COOP_MULTIPLAYER.md` 为 Host 权威架构，本方案涉及的状态变更必须同步：

| 变更 | 需要动的联机位置 |
|---|---|
| 能量回复速率 | `BALANCE` 常量为双端共享，仅需两端版本一致 |
| 附魔区域施加 | `src/systems/CardSystem.js` 的 `sendPlayCardCommand` 载荷、`src/network/host/CommandValidator.js:validateCard`、`src/network/host/SnapshotBuilder.js` |
| 附魔等级 +1 | 附魔结果由 host 结算并进快照，client 只做表现 |

**新增的协议字段必须在 host 侧校验（点数合法性、半径上限、受影响单位归属），不能信任 client 传来的单位列表。**

## 五、验证方式

```powershell
node --check src/systems/CardSystem.js
node --check src/data/gameData.js
npm run build
```

游戏内人工验证清单：
1. 一局标准关卡打完，记录同屏最大友方单位数（与改动前对比）。
2. 附魔区域施加能否正确命中范围内全部友方单位，且不给敌方/建筑施加。
3. 附魔等级是否随同名重复施加正确递增，5 槽上限是否仍然生效。
4. 双人联机：区域附魔后双方附魔状态与能量扣除是否一致。
5. 移动端：区域模式下的半径预览与高亮是否可读、不遮挡单位。
